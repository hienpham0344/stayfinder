# Preferences, support and in-app notifications
GET/PATCH /api/users/me/preferences are owned JWT routes. The defaults are en-US and bookingNotifications=true; patches accept language (en-US/vi-VN/fr-FR) and/or bookingNotifications only. Language controls formatting in the app, rather than promising full app translation. User role, wallet and auth email cannot be edited here.

POST /api/support/reports accepts category Booking/Payment/Account/Rewards/Other, description1–5000 and optional owned bookingId. Its response is reportId/status submitted/createdAt. No email/push/follow-up is sent or promised. The optional Idempotency-Key enables a stable retry/result; clients without it create a new request for each submission. Do not put report text in logs or URLs.

GET /api/notifications returns the normal pagination fields plus a server-issued snapshotTime. GET /unread-count returns count. PATCH /{id} accepts read=true only and marks an owned item idempotently. POST /read-all requires the unmodified snapshotTime from an inbox response and returns updated/unreadCount. Clients must preserve the full timestamp string instead of rounding through Date. After read-all, deliveries newer than that inbox snapshot stay unread.

Notification insertion and outbox completion share a transaction. Worker batches100 rows with FOR UPDATE SKIP LOCKED, then acquires owner inbox mutexes in sorted UUID order before publishing. This lock namespace is separate from financial wallets. Unique event/user prevents duplicate delivery; failed transactions leave events pending. Outbox disposition records delivered/suppressed/unsupported/invalid_source. Booking/payment/refund notices honor bookingNotifications; reward notices still appear. Targets are an owned booking UUID or the fixed Rewards route only.

Inbox list persists a per-owner server watermark in notification_inbox_state while holding the inbox mutex. Later deliveries receive timestamps after the most recent issued cutoff, including equal clock precision. Read-all cannot use a cutoff beyond a server-issued snapshot. No notification is dated from an old event time that would make a later delivery look earlier than the inbox snapshot. Mark-read timestamps do not precede their delivery timestamp.
